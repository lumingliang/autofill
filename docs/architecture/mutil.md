# 多租户改造需求文档

## 一、概述

本文档指导如何将现有系统改造为多租户架构。系统已具备基础多租户能力（租户模型、用户-租户关联），需要完善租户管理功能和数据隔离机制。

## 二、核心设计原则

### 2.1 超级管理员标识
- **统一使用 `is_superuser` 字段判断超级管理员身份**
- 前端通过 `userStore.isSuperUser` 判断
- 后端通过 `user.is_superuser` 判断
- **废弃 `username === 'root'` 的硬编码判断方式**

### 2.2 角色分级
| 角色类型 | 标识方式 | 权限范围 |
|---------|---------|---------|
| 系统超级管理员 | `is_superuser=true` | 管理所有租户、系统级菜单/API |
| 租户管理员 | 拥有租户管理员角色 | 管理指定租户下的数据和用户 |
| 普通用户 | 普通角色 | 按分配的角色访问对应功能 |

## 三、功能模块改造

### 3.1 登录流程改造

#### 3.1.1 超级管理员登录
- 使用配置文件中的账号（root/root）登录
- 登录后直接进入系统，无需选择租户
- 可访问「租户管理」菜单

#### 3.1.2 普通用户登录
- 查询用户关联的所有租户
- **如果用户只属于一个租户**：直接登录，设置 `current_tenant_id`
- **如果用户属于多个租户**：弹窗让用户选择租户，选择后设置 `current_tenant_id`

#### 3.1.3 登录接口返回
```json
{
  "access_token": "xxx",
  "username": "admin",
  "tenants": [{"id": 1, "name": "租户A", "domain": "a.com"}],
  "need_select_tenant": false,
  "current_tenant_id": 1
}
```

### 3.2 租户管理模块（仅超管可见）

#### 3.2.1 功能清单
- 租户列表（分页、搜索）
- 新增租户
- 编辑租户
- 删除租户（逻辑删除）

#### 3.2.2 租户关键字段
| 字段 | 类型 | 说明 |
|-----|-----|-----|
| name | string | 租户名称 |
| domain | string | 租户域名标识 |
| is_active | boolean | 是否启用 |
| description | string | 租户描述 |

#### 3.2.3 创建租户时的自动操作
创建租户后，系统自动执行：
1. 创建该租户的管理员角色（`tenant_admin_{tenant_id}`）
2. 为该角色分配**所有菜单和API权限**
3. 超管可将此角色分配给租户下的用户

### 3.3 用户管理模块改造

#### 3.3.1 列表页改造
| 改造项 | 超管可见 | 普通用户可见 |
|-------|---------|-------------|
| 租户字段列 | ✅ | ❌ |
| 租户下拉筛选 | ✅ | ❌（只能看当前租户用户） |

#### 3.3.2 新增/编辑用户改造
| 改造项 | 超管 | 普通用户 |
|-------|------|---------|
| 选择租户（多选） | ✅ 下拉多选 | ❌ 自动归属当前租户 |
| 分配角色 | ✅ 可选任意租户的角色 | ❌ 只能选当前租户的角色 |

**关键逻辑**：
- 超管为用户分配角色时，先选择租户，再查询该租户下的角色列表
- 这样超管可以将「租户管理员角色」分配给用户，使其具备管理该租户的权限

### 3.4 角色管理模块改造

#### 3.4.1 列表页改造
| 改造项 | 超管可见 | 普通用户可见 |
|-------|---------|-------------|
| 租户字段列 | ✅ | ❌ |
| 租户下拉筛选 | ✅ | ❌ |

#### 3.4.2 新增/编辑角色改造
| 改造项 | 超管 | 普通用户 |
|-------|------|---------|
| 选择所属租户 | ✅ 下拉单选 | ❌ 自动归属当前租户 |

#### 3.4.3 权限设置改造（关键）
**当前问题**：设置权限时，菜单列表和API列表没有进行数据隔离

**改造方案**：

**方案A（推荐）：根据当前用户角色过滤**
- 超管：可以看到所有菜单和API
- 租户管理员：只能看到自己有权限的菜单和API，只能分配自己拥有的权限给下属角色

**方案B：根据角色所属租户过滤**
- 加载菜单/API时，根据当前正在设置的角色所属租户进行过滤
- 需要为菜单和API增加 `tenant_id` 字段

**接口改造**：
```python
# 获取菜单列表（需要数据隔离）
GET /api/v1/menus/list
- 超管：返回所有菜单
- 普通用户：返回该用户有权限的菜单

# 获取API列表（需要数据隔离）  
GET /api/v1/apis/list
- 超管：返回所有API
- 普通用户：返回该用户有权限的API
```

### 3.5 菜单和API的数据隔离

#### 3.5.1 当前问题
- 菜单表和API表没有 `tenant_id` 字段
- 所有租户共享同一套菜单和API定义

#### 3.5.2 改造方案
**保持现状，通过权限控制实现隔离**：
- 菜单和API作为系统级资源，不区分租户
- 通过「角色-菜单」「角色-API」的关联关系实现隔离
- 租户管理员只能看到自己角色拥有的菜单和API

## 四、数据隔离机制

### 4.1 隔离策略

| 数据类型 | 隔离方式 | 说明 |
|---------|---------|-----|
| 用户 | `user.tenants` 多对多关联 | 用户可属于多个租户 |
| 角色 | `role.tenant_id` 字段 | 角色归属特定租户或系统 |
| 部门 | `dept.tenant_id` 字段 | 部门归属特定租户 |
| 菜单 | 不隔离，通过权限控制 | 系统级资源 |
| API | 不隔离，通过权限控制 | 系统级资源 |

### 4.2 后端数据隔离中间件

```python
# 伪代码：数据隔离中间件
async def tenant_isolation_middleware(request, call_next):
    user = await get_current_user(request)
    
    # 超管跳过隔离
    if user.is_superuser:
        return await call_next(request)
    
    # 检查用户是否选择了租户
    if not user.current_tenant_id:
        return error_response("请先选择租户")
    
    # 设置当前租户上下文
    set_tenant_context(user.current_tenant_id)
    
    # 查询时自动添加 tenant_id 过滤
    response = await call_next(request)
    return response
```

### 4.3 各模块数据隔离规则

#### 用户管理
- 超管：可查看所有用户，可按租户筛选
- 租户管理员：只能查看 `user.tenants` 包含当前租户的用户

#### 角色管理
- 超管：可查看所有角色，可按租户筛选
- 租户管理员：只能查看 `role.tenant_id = 当前租户ID` 的角色

#### 部门管理
- 超管：可查看所有部门，可按租户筛选
- 租户管理员：只能查看 `dept.tenant_id = 当前租户ID` 的部门

## 六、前端改造清单

### 6.1 超级管理员判断统一

**修改前**：
```javascript
// 混合使用两种方式
const isRootUser = computed(() => {
  return userStore.userInfo?.username === 'root' || userStore.userInfo?.is_superuser
})
```

**修改后**：
```javascript
// 统一使用 is_superuser
const isSuperUser = computed(() => {
  return userStore.userInfo?.is_superuser
})
```

## 七、实现优先级

### 第一阶段：基础功能
1. 统一 `is_superuser` 判断逻辑
2. 完成租户管理模块（增删查改）
3. 完成登录时租户选择功能

### 第二阶段：数据隔离
1. 用户管理模块数据隔离
2. 角色管理模块数据隔离
3. 后端数据隔离中间件

### 第三阶段：权限细化
1. 菜单/API列表的数据隔离（根据用户权限过滤）
2. 租户管理员只能分配自己拥有的权限
3. 完善权限校验逻辑

## 八、注意事项

1. **不要修改现有表结构**：系统已具备 `tenant` 表和关联关系，在此基础上扩展功能即可
2. **保持向后兼容**：改造过程中确保现有功能正常运行
3. **权限最小化原则**：非超管用户只能访问自己有权限的数据和功能
4. **租户隔离严格性**：一个租户的数据绝不能被其他租户访问
